I Turned My Instagram Saves Into a Trip Planner (Laravel + Filament + Local AI)

By Sonali Dudhia • September 8, 2026 • 11 min read

Laravel Filament AI Ollama Side Project

🎀 The Spreadsheet Problem

I travel like a local. I want the neighbourhood bakery, not the postcard thing. And I am an Instagram girlie 💅 — my saved collection is where all of that lives: reels of tiny food spots, viewpoints nobody queues for, and "do not miss this" tips from people who actually live there. My saves folder is basically a travel guide written by strangers who love me.

The problem is what comes next. Planning meant opening every saved reel one by one 😵‍💫, typing place names into a spreadsheet, googling each one to work out where it actually is, and then trying to shape that mess into an itinerary. Hours of it. For a trip that is supposed to be fun.

So I built the thing I wanted 🛠️. Paste a reel link, get the places back: name, what it is, why it was worth saving, grouped by country and city, with a switch for the ones I refuse to miss. It runs entirely on my own machine. No API keys, no subscriptions, nothing sent anywhere. 🔒

It is called reel2trip, and it is open source on GitHub. Here is what it looks like end to end:

✅ What I Wanted It to Do

Before writing anything, I wrote down the short version of the product:

  • 📎 Accept an Instagram reel URL and do the rest without further input.
  • 🎧 Read both the spoken audio and the caption, because half the tips live in each.
  • 📋 Return a structured list of places, not a paragraph of prose.
  • 🌍 Resolve each place to a country and city so results can be grouped.
  • ⭐ Let me mark a city as one I am visiting, and a place as a must-do.
  • 💻 Run offline, on my laptop, with no third-party account involved.

Everything else, including the itinerary generation I originally sketched out, was optional. That distinction turned out to matter more than I expected.

🗺️ High-Level Architecture

Instagram Reel URL
    |

Each arrow in that diagram is a stage of one queued job. That is the whole system. The interesting parts are the extraction step and what happens when it goes wrong.

🔑 Why Zero API Keys

Running everything locally was a design constraint I set at the start, not a compromise I settled for later.

The first reason is privacy. My saved collection is a fairly precise map of where I am going, what I like, and when I will be away from home. That is not data I want sitting in someone else's logs.

The second is cost shape. A hosted model charges per request, and the natural instinct when processing costs money is to batch carefully and avoid retries. Local inference costs electricity and time, which means I can re-run extraction on the same reel five times while tuning a prompt and not think about it once.

The third is distribution. Anyone can clone the repository, run ollama pull, and have a working app. There is no signup step, no key to provision, and no environment variable that silently breaks the demo for everyone else.

None of this would have been practical a couple of years ago. Small local models have become good enough at constrained extraction that a self-hosted pipeline is now a reasonable default for this class of problem, rather than a purity exercise.

🤖 The Extraction Agent

The extraction step takes two inputs, the transcript and the caption, and returns an array of place objects. I used an agent class from laravel/ai pointed at a local Ollama model, with a schema describing the exact shape I expect back.

The agent itself stays small. Instructions, model, schema:

namespace App\Ai\Agents;

use App\Ai\Schemas\PlaceListSchema;

final class PlaceExtractionAgent extends Agent
{
    public function model(): string
    {
        return config('trip.extraction_model');
    }

    public function instructions(): string
    {
        return view('ai.prompts.place-extraction')->render();
    }

    public function schema(): array
    {
        return PlaceListSchema::definition();
    }
}

The schema is where the real specification lives:

final class PlaceListSchema
{
    public const CATEGORIES = [
        'restaurant', 'cafe', 'bar', 'viewpoint',
        'museum', 'shop', 'beach', 'activity', 'other',
    ];

    public static function definition(): array
    {
        return [
            'type' => 'object',
            'properties' => [
                'places' => [
                    'type' => 'array',
                    'items' => [
                        'type' => 'object',
                        'required' => ['name', 'category'],
                        'properties' => [
                            'name' => ['type' => 'string'],
                            'city' => ['type' => 'string'],
                            'category' => ['type' => 'string', 'enum' => self::CATEGORIES],
                            'description' => ['type' => 'string'],
                            'tip' => ['type' => 'string'],
                            'price_hint' => ['type' => 'string'],
                        ],
                    ],
                ],
            ],
        ];
    }
}

Six fields, and each one earns its place. name is what I search for later. city gives the geocoder a hint so a common restaurant name does not resolve to the wrong continent. category is a closed enum so filtering stays reliable. description is one line on what the place is. tip is the part that makes the whole thing worth building, the specific advice from the reel, such as which dish to order or what time to arrive. price_hint is free text because reels describe prices in wildly inconsistent ways.

The system prompt does the work the schema cannot. It defines what counts as a place, and it is unusually direct about what not to do: 

You extract places from a short travel video.

You are given a transcript and a caption. Both may be
incomplete, informal, or in mixed languages.

Rules:
- Only extract places a traveller could visit. Ignore
  brands, hotels the creator is sponsored by, and generic
  advice such as "eat local food".
- Use the exact name as spoken or written. Do not translate
  it, expand abbreviations, or correct spelling.
- If the city is not stated, leave city empty. Never guess.
- category must be one of the listed values. If none fit,
  use "other".
- tip must come from the video. If there is no tip, leave
  it empty rather than inventing one.
- Return an empty places array if the video contains no
  specific places.

"Return an empty array" needs to be said out loud. Without it, a small model asked to extract places will find places, even in a reel that is just someone narrating a sunset.

🫠 What Small Local Models Actually Get Wrong

This is the section I would have wanted to read before starting.

Structured output constrains the shape of the response, not its sense. Every failure I hit was syntactically valid JSON that parsed cleanly and was still wrong. The schema said yes. The data said absolutely not. Three patterns showed up repeatedly:

Failure What it looks like Why it happens
😶 Empty or placeholder values A required name comes back as "" or "Unknown Restaurant" The model would rather satisfy the schema than return nothing
🥴 Near-miss enum values "wiewpoint", "Viewpoint", "view point" Enum enforcement varies by model and runtime, so I stopped assuming it
🎨 Invented categories "streetfood", "nature" instead of "other" Nothing in the enum fits, and falling back feels like giving up

So I stopped treating extraction as one call and started treating it as a validate-and-repair loop. Everything the model returns goes through normal Laravel validation first: 

use Illuminate\Validation\Rule;

public function rules(): array
{
    return [
        'places' => ['present', 'array'],
        'places.*.name' => ['required', 'string', 'min:2', 'max:120'],
        'places.*.city' => ['nullable', 'string', 'max:120'],
        'places.*.category' => ['required', Rule::in(PlaceListSchema::CATEGORIES)],
        'places.*.description' => ['nullable', 'string', 'max:400'],
        'places.*.tip' => ['nullable', 'string', 'max:400'],
        'places.*.price_hint' => ['nullable', 'string', 'max:60'],
    ];
}

The repair strategy has three levels, applied in order.

Level one is deterministic coercion. Anything fixable without a model gets fixed without a model: trim whitespace, lowercase the category, map a small alias table of known near-misses, and convert placeholder strings to null. This handles the majority of problems at effectively zero cost.

Level two is a targeted re-prompt. If validation still fails, I send the model its own output back along with the specific validation messages, and ask it to correct only the invalid entries. The key detail is that the errors are attached verbatim. A message like "the category field must be one of restaurant, cafe, bar..." is far more effective than restating the schema in prose.

Level three is partial salvage. If an item still fails after the repair pass, I drop that item and keep the rest, recording the failure against the reel. A reel that yields four good places and one unusable fragment should give me four places, not an exception. Failing the whole batch over one bad row is the behaviour that makes local models feel unusable, and it is entirely avoidable.

This logic ended up being generic enough that I am pulling it out into a small package. It has nothing to do with travel, and everything to do with the fact that the gap between "valid JSON" and "usable data" is where most of the work in a local AI pipeline actually sits.

⚙️ The Job Pipeline

Downloading a video, transcribing it, and running local inference are all slow and all fail for different reasons. Instagram rate limits. Whisper occasionally chokes on a file. The model is simply not fast.

Because of that, the processing job is written as a sequence of idempotent stages, each of which checks whether its work is already done before doing it. A retry after a rate limit resumes where it stopped instead of paying for the expensive local inference twice. 

public function handle(
    ReelDownloader $downloader,
    Transcriber $transcriber,
    PlaceExtractor $extractor,
    Geocoder $geocoder,
): void {
    $reel = $this->reel->fresh();

    if (! $reel->media_path) {
        $reel->update($downloader->fetch($reel->url));
    }

    if (! $reel->transcript) {
        $reel->update([
            'transcript' => $transcriber->transcribe($reel->media_path),
        ]);
    }

    if ($reel->places()->doesntExist()) {
        $extractor->extract($reel);
    }

    $geocoder->resolvePending($reel);

    $reel->update(['status' => ReelStatus::Completed]);
}

The job is configured with a small number of tries, a backoff, and a WithoutOverlapping middleware keyed on the reel ID, so the same reel can never be processed twice concurrently. Geocoding is its own method because Nominatim asks for a request rate limit, and resolvePending() only touches places that do not have coordinates yet.

Writing stages this way costs a few extra conditionals and removes an entire category of problem. A failed run is never destructive, so retrying is always safe.

🖥️ Filament v4 as the Whole UI

There is no separate frontend. The Filament panel is the product. 😌

That decision saved weeks. I did not build authentication, a table component, a form layout, a notification system, or a dark mode. I built two resources and one custom page, and the rest came with the panel.

The Reels resource is where links go in and progress comes back. The status column is a badge, and the table polls so a reel moves from pending to completed while I am looking at it: 

public function table(Table $table): Table
{
    return $table
        ->poll('5s')
        ->columns([
            TextColumn::make('url')->limit(50)->label('Reel'),
            TextColumn::make('status')
                ->badge()
                ->color(fn (ReelStatus $state) => match ($state) {
                    ReelStatus::Pending => 'gray',
                    ReelStatus::Processing => 'warning',
                    ReelStatus::Completed => 'success',
                    ReelStatus::Failed => 'danger',
                }),
            TextColumn::make('places_count')->counts('places')->label('Places'),
            TextColumn::make('created_at')->since()->label('Added'),
        ])
        ->recordActions([
            Action::make('reprocess')
                ->requiresConfirmation()
                ->action(fn (Reel $record) => ProcessReel::dispatch($record)),
        ]);
}

A five second poll on a table with a handful of rows is not a performance concern, and it removes the need for any realtime infrastructure. The reprocess action exists because prompt changes are frequent and re-running one reel should be a single click.

The Places resource handles everything after extraction: editing a name the model transcribed oddly, correcting a category, or deleting something that was never a place to begin with. It is a standard Filament resource, which is the point.

The page I actually use is a custom one. Places are grouped country to city to place. Each city has a "visiting" toggle, each place has a "must-do" toggle, and both write straight to the database through Filament's built-in state handling. Countries with nothing marked as visiting collapse out of the way, so what remains on screen is the trip I am planning rather than the entire archive of everything I ever saved.

✂️ The Feature I Cut

I nearly built automatic day-planning. The plan was genuinely quite neat: cluster geocoded places by distance, assign one cluster per day, order each day to minimise walking, and hand over a finished itinerary. I had the clustering half-written before I stopped.

What stopped me was thinking about an actual trip. Real trips have internal flights that eat a morning. Car days where distance stops mattering. Places that only open on certain days. Reservations booked months ahead that anchor an entire evening. Nights that end late enough to make the next morning theoretical. The algorithm does not know I will be hungover. 🍷

The algorithm would have had an opinion about all of that, and its opinion would have been wrong on day one. Then I would have spent my evening fighting the planner instead of planning. The honest version is that I wanted to build the clustering because clustering is fun to build, which is a reason to build something, but not a reason to ship it.

So I shipped a list with toggles. It knows nothing about my schedule, which is exactly why it never gets my schedule wrong. Every real constraint lives in my head or in a booking confirmation, and the tool's job is to make sure I have the right options in front of me when I apply them. Constraint-free tooling beat the clever algorithm because the clever algorithm needed to model a world it had no access to.

There is a version of this feature I would build later, and it is much smaller: a "places near here" filter that answers a question I ask, rather than a planner that makes a decision for me.

📌 Things That Mattered

  • Treat structured output as a shape guarantee only. Validate the meaning separately.
  • Fix deterministically fixable errors in code before spending another inference call on them.
  • Attach the actual validation messages when re-prompting. Restating the schema is weaker.
  • Salvage valid items instead of failing the batch on one bad row.
  • Make every job stage idempotent so a retry never repeats expensive local inference.
  • Feed the caption to the model alongside the transcript. Names are usually written, not spoken.
  • Give the geocoder a city hint, and keep coordinates nullable rather than blocking on them.
  • Tell the model explicitly that returning nothing is a valid answer.

💡 Why This Stack Worked

Laravel handled the parts of an AI application that are not really about AI: queueing slow work, retrying it safely, validating untrusted input, and persisting results. Model output is untrusted input, and the framework already had the right tools for it.

Ollama made local inference an implementation detail. Swapping models during development was a config change, which meant I could compare a smaller and larger model on the same reel without touching application code.

Filament removed the frontend entirely. For a tool with one user, the admin panel is not a stand-in for the product, it is the product, and building it that way is what let a side project reach the point of being genuinely useful instead of stalling at eighty percent.

🌸 Final Thoughts

The test I set was simple: could it plan a real trip. It did. 🎉 I pasted in a collection of saved reels, got back a grouped list of places with the tips still attached, marked the cities I was going to and the handful of places I was not willing to miss, and used that list on the ground. The spreadsheet never happened. 📊🚫

What I did not expect was how much of the work was ordinary application engineering. The model is one call in the middle of a pipeline. The rest is validation, retries, idempotency, and a UI that respects the fact that the extraction will sometimes be wrong.

The repository is public and MIT licensed. Clone it, pull a model, and it runs on your machine with nothing to sign up for. If you build something on top of the extraction and repair layer, I would like to hear about it. 🎀
